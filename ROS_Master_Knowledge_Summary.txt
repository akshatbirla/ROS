ROS MASTER KNOWLEDGE SUMMARY

This document is a consolidated summary of the project’s vision,
architecture, philosophy, workflow, engineering standards, UI direction,
documentation strategy, and future roadmap. It is based on the planning
discussions and the existing master planning document. It is intended as
a long-form reference for future AI coding agents and human
contributors.

Project Vision

ROS is envisioned as a digital operating system for a Rotaract Club. It
is intended to replace scattered spreadsheets, reports, forms, media
folders, attendance sheets, finance records, and institutional knowledge
with one coherent platform. The first deployment targets the Rotaract
Club of Acropolis Royals. The long-term vision is district adoption and
eventually a platform that can serve multiple clubs while preserving
history through Rotary Years.

Architecture

The preferred stack is React, TypeScript, Vite, Tailwind CSS, shadcn/ui,
TanStack Query, Zustand, Supabase, PostgreSQL, Google Drive for storage,
and Google Sheets for import and export. Google Drive stores media while
the database stores metadata. Google Sheets is never treated as the
primary database.

Engineering

The project values maintainability, readability, scalability,
documentation, testing, and beautiful UX over shortcuts. Every feature
should be implemented as a vertical slice from database to UI, tested
and documented before moving on.

UI Philosophy

The visual direction is inspired by Apple Vision Pro, Iron Man JARVIS,
premium SaaS products, dark luxury, glassmorphism, and smooth purposeful
animations. The application should feel alive rather than like a generic
admin dashboard.

Future

Future expansion includes AI assistants, report generation, district
support, notifications, PWAs, OCR, analytics, sponsorship management,
and multi-club support, but these remain out of scope for the initial
release.

Engineering Principle 1

The long-term objective of ROS is to create software that remains
understandable and maintainable across multiple Rotary Years. Each
module should have a single responsibility. Documentation should evolve
alongside the code. Every feature should be reviewed for usability,
accessibility, responsiveness, validation, error handling, testing, and
future extensibility. Google Drive should be used for long-term media
storage, while structured business data belongs in the database. Google
Sheets should serve as an import/export bridge for existing club
workflows until native workflows fully replace them. The dashboard
should function as a command center rather than a traditional
administrative page. The design language should remain consistent,
premium, minimal, and focused on reducing cognitive load. Whenever
architecture changes, documentation should be updated immediately. This
principle reinforces the project’s emphasis on quality over shortcuts,
long-term thinking over temporary convenience, and sustainable
engineering over rapid but fragile implementation.

understandable and maintainable across multiple Rotary Years. Each
module should have a single responsibility. Documentation should evolve
alongside the code. Every feature should be reviewed for usability,
accessibility, responsiveness, validation, error handling, testing, and
future extensibility. Google Drive should be used for long-term media
storage, while structured business data belongs in the database. Google
Sheets should serve as an import/export bridge for existing club
workflows until native workflows fully replace them. The dashboard
should function as a command center rather than a traditional
administrative page. The design language should remain consistent,
premium, minimal, and focused on reducing cognitive load. Whenever
architecture changes, documentation should be updated immediately. This
principle reinforces the project’s emphasis on quality over shortcuts,
long-term thinking over temporary convenience, and sustainable
engineering over rapid but fragile implementation.
